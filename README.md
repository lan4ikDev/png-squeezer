# PNG Squeezer

Локальный аналог [TinyPNG](https://tinypng.com/) с изменением размера в духе
[iLoveIMG](https://www.iloveimg.com/ru/resize-image). Работает офлайн, файлы
никуда не отправляются.

Под капотом та же связка, что и у TinyPNG:

```
RGBA  →  libimagequant (медианный срез)  →  палитра подбирается под качество
      →  oxipng (перебор фильтров, deflate, уменьшение битности палитры)
```

Размер палитры не фиксирован: инструмент бинарным поиском находит **самую
маленькую палитру, которая ещё проходит порог качества** (256 → 192 → 144 →
112 → 80 → 64 → 48). Кадру, который выглядит так же с 48 цветами, незачем
отдавать 256 — именно на этом и берётся основная экономия.

На наборе из 611 игровых текстур (тёмные 3D-рендеры, много прозрачности):
**296 МБ → 81 МБ, то есть −72.6 %**, при **побитово неизменном альфа-канале**.
Светлые детализированные кадры сжимаются на −79 %, фоны — на −88…−89 %, тёмные
кадры анимаций — на −56…−69 %.

## Запуск

**Готовое приложение:** `PNG Squeezer.exe` — один файл на 33 МБ, ничего не
требует, Python внутри не нужен. Окно открывается примерно за 2.5 секунды.
Файлы и папки можно бросать прямо на его иконку — они сразу попадут в список.

Из исходников, если Python установлен:

```
py -m pip install -r requirements.txt
py -m png_squeezer
```

Либо двойной клик по `PNG Squeezer.bat` — он сам поставит зависимости при
первом запуске.

## Сборка .exe

```
py -m pip install pyinstaller
py build_exe.py --dest "%USERPROFILE%\Desktop"
```

`build_exe.py` рисует иконку, собирает всё в один файл и кладёт результат
куда указано. Ключ `--onedir` соберёт папкой — стартует чуть быстрее, но это
уже не один файл.

Сборка обязана явно забрать с собой `tkinterdnd2` (в нём лежит скомпилированный
Tcl-пакет `tkdnd`, который PyInstaller не видит через загрузчик Tcl) и
`imagequant` (cffi-расширение). Это уже прописано в `build_exe.py`.

## Два инструмента

| Вкладка | Что делает | Настройки |
|---|---|---|
| **Сжатие** | Квантование в 8-битную палитру + перепаковка | скрыты за иконкой ⚙ — умолчания подходят почти всегда |
| **Изменить размер** | Масштабирование в процентах или пикселях, затем сжатие | панель открыта сразу |

## Два способа получить результат

Выбираются независимо от вкладки:

- **Сохранить в ZIP** — исходные файлы не трогаются, результат отдаётся одним
  архивом через обычное окно сохранения Windows, потом предлагается открыть его.
- **Заменить на месте** (bypass) — каждый файл перезаписывается сжатым. Если
  бросить папку в этом режиме, обработка начинается сразу.

Файлы и папки можно перетаскивать в окно или выбирать кнопками.

### Интерфейс

Окно нарисовано вручную на `tk.Canvas` — ttk на Windows не отдаёт свою
системную рамку, какой стиль ему ни задай. Анимации идут от одного общего
таймера в `animation.py`: у каждого виджета свой `after`-цикл означал бы
десятки конкурирующих таймеров.

Что двигается: подсветка вкладок скользит между сегментами, кнопки плавно
разгораются под курсором и вдавливаются при нажатии, галочки прорисовывают
себя, зона перетаскивания разгорается и тянется к файлу, у обрабатываемого
файла вращается дуга, полоски экономии и итоговые цифры вырастают до своих
значений, а список прокручивается с инерцией.

### Подпапки

Папки обходятся **рекурсивно на любую глубину**: выбрали одну папку — будут
обработаны все PNG во всех вложенных папках. Строка состояния показывает, что
именно набралось («43 файла в 7 папках»), а в списке у файлов видны
относительные пути (`close/1.png`, `enter/2.png`), так что понятно, откуда они.

Отключается галочкой **«Включая подпапки»** под иконкой ⚙ — тогда берётся
только верхний уровень выбранной папки. В командной строке это `--no-recursive`.

Пути с пробелами и кириллицей обрабатываются нормально; файлы `.bak` и всё,
что не `.png`, пропускаются; одна и та же папка, добавленная дважды, не
обрабатывается дважды.

### Сглаживание при изменении размера

Ползунок **«Сглаживание»** 0..100 на вкладке размера. До 40 работает Lanczos
(максимально резко), выше — bicubic, а после 60 добавляется небольшое
гауссово размытие до 0.8 px. По умолчанию 50.

Он появился потому, что один Lanczos оставлял заметно более «пиксельную»
картинку, чем дают онлайн-резайзеры, а шаг квантования это ещё и усиливает:
после перевода в палитру детализация подскакивает с 6.93 до 7.40, потому что
плоские блоки цвета читаются как блочность.

Размытие применяется через premultiplied alpha — иначе цвет, спрятанный под
полностью прозрачными пикселями (обычно чёрный), затекал бы в видимый край и
спрайты получали бы тёмную кайму.

## Что инструмент не сломает

Проверено тестами, а не обещаниями:

- **Альфа-канал не меняется ни на бит.** Если квантование его тронуло бы,
  результат отбрасывается и остаётся вариант без потерь.
- **Отличие измеряется дважды.** Считается среднее отклонение видимых
  пикселей (взвешенно по альфе) — и оно же **относительно собственного
  контраста кадра**. Второе появилось не просто так: на тёмном кадре, где все
  значения лежат в диапазоне 0..36, картинку можно расплющить до двух
  оттенков, и абсолютная ошибка останется около 1 %. Кадр отклоняется, если
  превышен любой из порогов.
- **Палитра не схлопывается.** Поиск не опускается ниже 48 цветов, и это
  главная защита. Ползунок «Качество» задаёт бюджет ошибки, а не потолок для
  libimagequant: потолок — ловушка, библиотека, обнаружив, что может сделать
  лучше него, начинает *намеренно выбрасывать цвета*, и на тёмной графике её
  метрика остаётся высокой даже при двух оттенках (испорченный двухцветный
  кадр она оценивает в 99 из 100).

  Порог в 48 цветов подобран не по формуле, а глазами, потому что никакая
  простая статистика ошибки здесь не работает: у яркой детализированной
  текстуры при 128 цветах она **выше**, чем у тёмного кадра, расплющенного до
  20, — детали маскируют ошибку, а ровная тень нет. Зато чётко разделился сам
  размер палитры: всё от 28 цветов и выше выглядело правильно, всё от 20 и
  ниже теряло блики.

  Судить надо при той яркости, при которой кадр видит зритель. Фон комнаты
  ужимается с 44820 цветов до 48, и при поднятой гамме на стенах видно лёгкое
  полошение — но при натуральной яркости оригинал, 48, 96 и 160 цветов
  неотличимы, а стоят 114 КБ против 198 КБ.
- **Файл никогда не растёт.** Если сжатый вариант оказался больше исходного,
  берётся исходный.
- **Повторный запуск ничего не портит.** Уже сжатый файл распознаётся как
  8-битная палитра и только перепаковывается без потерь — второй проход даёт
  нулевой дрейф размера и ноль изменённых пикселей.
- **Анимированные PNG не трогаются** — ни квантования, ни изменения размера,
  иначе от анимации остался бы первый кадр.
- **Запись атомарна.** Новые байты пишутся в соседний временный файл и
  переносятся через `os.replace`, так что прерывание не оставит половину
  картинки. Опционально рядом кладётся копия `.bak`.

## Командная строка

Для пакетной работы окно не нужно:

```
py -m png_squeezer "путь\к\папке" --dry-run           # посчитать, ничего не менять
py -m png_squeezer "путь\к\папке" --in-place          # сжать и заменить
py -m png_squeezer "путь" -o out.zip                  # сложить результат в архив
py -m png_squeezer "путь" --percent 50 --in-place     # уменьшить вдвое
py -m png_squeezer "путь" --width 512 --in-place      # ширина 512, высота пропорционально
py -m png_squeezer "путь" --smoothing 80 --percent 50 # мягче при уменьшении
py -m png_squeezer "путь" --lossless --in-place       # только перепаковка без потерь
```

`--help` покажет остальные ключи (`--quality`, `--colors`, `--effort`,
`--dither`, `--backup`, `--jobs`, `--no-recursive`).

## Заметка для геймдева

Сжатие PNG уменьшает размер репозитория и сборки, **но не занимаемую
видеопамять.** Движок всё равно распаковывает текстуру в RGBA8 в VRAM, так что
выигрыш будет в объёме пакета и скорости загрузки, а не в потреблении памяти.

После замены файлов на месте Godot переимпортирует их при следующем открытии
редактора; `.import`-файлы трогать не нужно.

## Зависимости

`Pillow`, `numpy`, `imagequant` (libimagequant), `pyoxipng`, `tkinterdnd2`
(только для перетаскивания — без неё окно работает, но файлы придётся
выбирать кнопками). Без `imagequant`/`pyoxipng` инструмент не падает, а
переходит в режим сжатия без потерь и говорит об этом в строке состояния.

## Замечание про HiDPI

Окно намеренно оставлено DPI-unaware: Windows масштабирует его целиком, и
вёрстка остаётся правильной на любом масштабе. На экранах с 150 % это стоит
лёгкой мягкости шрифтов.
